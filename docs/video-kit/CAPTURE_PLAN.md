## Take A — inputs and initial audit (one paid run)

1. Start the demo. Record initial description containing the unsupported waterproof promise and the ambiguous image caption. Scroll until the complete text is visible.
2. Open merchant specification. Hold the bottle exclusion and light-rain limitation for 4 seconds. Record the image source separately.
3. Click Run audit once and record the actual run activity until it completes. Keep uncut source footage. When editing, show `Analysis wait shortened` over every cut/compressed wait.
4. Inspect the generated outcomes: supported repair; unknown laptop fit; damaged zipper / delivery routed to human action. Read the output before filming claims about it. Model wording varies.
5. Open review, read the changed facts, check the factual-review checkbox, approve the actual patch. **Do not publish it yet** if capturing invalidation next.

## Take B — changed evidence and reassessment (one paid run)

6. Supply the complete synthetic specification, preserving original package and weather facts, adding only: `Laptop sleeve internal dimensions are 32 × 23 × 3 cm. Device compatibility has not been verified. Customers should measure their device, including any case.` Confirm it as merchant-provided synthetic data.
7. Record the real outdated approval/patch state. Film any rejected action only if the UI actually exposes it; never add a fake terminal code or fake error toast.
8. Reassess once. Film the actual dimensions and measurement advice. If the model does not produce a safe dimension change, retain the truthful result and describe the limitation. Never hand-edit a generated patch to fake success.
9. Review all facts and approve the new exact text. Keep the product page and evidence versions in shot.

## Take C — publish / verify / restore (no new model generation)

10. Publish the approved patch, open the demo storefront, refresh it and show the revised words. Current UI controls live in `app/workbench.tsx`; storefront in `app/store/[sku]/page.tsx`.
11. Run served-page verification. Hold its actual result. Explain that this checks the returned content/version, not customer understanding.
12. Restore the previous version, refresh the storefront, and verify the new restoration version. A rollback increments the version; it never rewinds the audit history.
13. Capture final history. If verification fails, show the real failure and manual restore option. Do not synthesize a green result.

## Paid-call stop condition

Read `docs/HANDOFF_GOOGLE_CLOUD.md` before Take A. Shared budget and daily capacity may be exhausted. Do not raise them. Stop after a failed paid run and inspect its reason before retrying; do not run loops to obtain attractive wording. At the last verified snapshot roughly USD0.20 remained in the workflow allowance, not a guaranteed number of runs. Two successful recordings may fit, but timeouts can use the allowance. Ask the owner if more budget becomes necessary; do not substitute a prerecorded response presented as live.
